# probes/pacing — straf3's frame-time distribution on the real GPU

Published: 2026-08-26.

The first frame-pacing numbers this repository has ever taken from the real GPU.
`--pacing-log` has written CSVs since wave 4; nothing had ever analysed one, and
PLAYING.md's "Not proven yet" list said so.

**Nothing in `results/**/*.csv` is hand-edited.** Each file is byte-exactly what
the client wrote at the end of its session, plus one machine-appended `#` line
recording what the host was doing during the run (see "The host", below). Every
fact about a run — the present mode the surface *granted*, the adapter, the
driver, the panel refresh, the build profile, the command line — is in the
file's own header, written by the process that took the measurement. That is
deliberate: a document beside a file can be attached to the wrong run, and prose
*inside* one of these files would be read as data.

This README is the prose. The numbers are in the CSVs and in the table below,
which is generated by the same tool that parses them rather than typed.

## The hardware and the build, stated once

| | |
|---|---|
| GPU | NVIDIA GeForce RTX 3060 Ti — `adapter_type=DiscreteGpu`, `backend=Vulkan` |
| GPU driver | Vulkan ICD `560.94` (`gpu_driver=NVIDIA`), vendor `0x10de`, device `0x2489` |
| Windows driver package | `32.0.15.6094` (WDDM version, supplied to the run as `host_wddm_driver=`, not observed by the process) |
| Panel | 1920×1080 at **165.000 Hz**, read off the monitor by the client: `refresh_mhz=165000` |
| Window | 1280×720 (`window_px`), windowed, on that panel |
| Build | `release`, `x86_64-pc-windows-gnu`, rustc 1.97.1, run as a native Windows process through WSL interop |
| Map | `assets/maps/coil.map` — 26 hulls, 4 triggers, **312 triangles** |
| Command rate | 125 Hz (8 ms), `profile=cpm` |

The renderer's own lines, from a session in this set:

```text
straf3-render: backend=Vulkan adapter="NVIDIA GeForce RTX 3060 Ti" type=DiscreteGpu
straf3-render: driver="NVIDIA" driver_info="560.94" vendor=0x10de device=0x2489
straf3-render: present_mode=immediate (requested immediate) frame_latency=2 available=[fifo,fifo_relaxed,mailbox,immediate]
```

`type=DiscreteGpu`, not `type=Cpu`: **no number here was taken on the WSL2
llvmpipe software rasteriser.** Every CSV carries `adapter_type=DiscreteGpu` in
its own header, so that is a property of the artefact and not a claim of this
document.

The two driver numbers are different identifiers and neither is the other:
`560.94` is what the Vulkan driver reports about itself, `32.0.15.6094` is the
Windows driver package version. Both are recorded, under their own names.

### Immediate is granted here, not merely requested

`available=[fifo,fifo_relaxed,mailbox,immediate]` and `present_mode=immediate
(requested immediate)` — no fallback. This settles a question that was open when
the wave began: the uncapped column below is a measurement of Immediate, not of
FIFO wearing Immediate's label. Every CSV records the **granted** mode under
`present_mode=`; a log that only knew what it asked for would say
`present_mode_requested=` instead, and the analysis prints a warning rather than
a mode.

## The method, before the numbers

### Three workloads, never pooled with each other

| set | what it is | runs |
|---|---|---|
| `results/static/` | An unattended session on `coil.map`, 62 s, `--no-pb`. | 3 per present mode |
| `results/frame-latency-1/` | The same, FIFO only, with `STRAF3_FRAME_LATENCY=1`. | 3 |
| `results/play/` | The same binary driven by a recorded run of the course, ~7 s, racing a ghost. | 3 per present mode |

**The "static" set is not a stationary camera.** The map carries the player
through the course — checked, not assumed: on `--world flat` the player never
moves at all, and on `coil.map` an unattended session reaches 689 ups and
crosses the finish line. So these are frames of a moving camera on a
312-triangle scene, on a trajectory that differs from run to run. That
variation is why the three runs are reported individually as well as together.

**The play set is a deterministic movement workload**, driving
`probes/coil-course/results/coil-run.txt` — 864 commands, 6912 ms of movement —
so the same frames are rendered in the same order every run. It is a good
measurement of *rendering* load and a poor one of *input handling*: its commands
come from a file, not from the event queue.

### Every run in a pooled set rendered the same scene

A personal best written by one run becomes the ghost the *next* run draws, and
the ghost is drawn into the same pass. That would make run 1 a lighter workload
than runs 2 and 3 — inside a set whose whole purpose is to hold the workload
fixed. So:

- the static and frame-latency sets run with `--no-pb`: no personal best can be
  loaded *or* written, and "no ghost in any of the three" is true by
  construction rather than by luck;
- the play set is seeded by a **throwaway run** that writes the personal best
  before any counted run starts, so all three counted runs load it, race it and
  draw it. The throwaway is not published and not counted.

There is a reason the static set could not simply be seeded instead: the
repository's committed personal best is **refused** by the current build —
*"this recording was made under physics profile `cpm` (5fb368a51a4697ec) and is
being replayed under 4350ccc31bec5d4c"*. That refusal is nine days old, not new:
`runs/coil.cpm.s3d` was committed on 2026-08-17 and the very next commit to
`crates/straf3-sim/src/` the same day moved the digest.

### The discard criterion, and the one revision made to it

**A run is discarded if and only if `cargo xtask pacing` observed compiler or
build processes consuming CPU on this host during it** — specifically, if in any
250 ms sample they together used at least 25 % of one core. The verdict is
printed before any statistic and is computed from `/proc`, never from the frame
times.

This matters more than it sounds. "Check for contention, then discard and
re-take" is a selection procedure, and if the criterion is the *result* rather
than the *cause* it manufactures the number it claims to measure: drop the runs
whose p99 looks bad, publish the survivors, and the distribution is an artefact
of the filter that looks exactly like a well-run measurement. The p99 is the
most exposed of all, because the tail is where a handful of excluded samples
move the answer.

**The criterion was revised once, and both versions belong here.** The first
version counted build processes that *existed*. It marked runs contended because
`rust-analyzer` — a long-lived editor daemon, idle, 3 samples out of 250, peak
load 0.74 — was in the process table. Presence is not contention; CPU time is. A
criterion that fires on nearly every run discriminates nothing.

Two things make that revision a correction rather than a tuning, and a reader is
entitled to check both:

1. it was made from **process behaviour**, not from frame times, and no
   distribution from any affected run had been read when it was made;
2. every run taken under the first criterion was **discarded wholesale** and the
   whole sweep re-taken, so nothing published was selected under two different
   rules.

### What "quiet" does and does not mean

It means *no build contended*. It does not mean the machine was idle: one run
reported `peak 0.00 cores, 0.00 CPU-seconds` of builder CPU while the Linux load
average peaked at 1.85 — other agent processes on this host, which the criterion
does not count. The load average is published beside the verdict rather than
folded into it. The watcher also sees only this WSL2 host's Linux side; load
inside another Windows process would be invisible to it.

### What these numbers are a claim about

They describe **straf3 on a machine doing nothing else**. A player with a
browser, a voice client and a stream encoder running sees a worse tail, and
nothing measured here bounds how much worse. Read as a condition, "165 fps,
p99 6.4 ms" is a claim about straf3; read without it, it would be a claim about
*playing* straf3, which was not measured.

### The ceiling

1920×1080 at 165 Hz. `docs/VISION.md` §15 asks for a 240 Hz-class responsiveness
budget; there is no 240 Hz display on this machine, so **that target is
unvalidated here**, and no number below speaks to it. Extrapolating a 6.06 ms
panel to a 4.17 ms one is arithmetic, not measurement.

### The trap this layout avoids

`xtask::pacing::parse_str` requires the first line of a log to be exactly
`# straf3 pacing log v2`, and reads *every* whitespace-separated `token=value`
on *any* `#` line as a header pair, first match winning. So a hand-written
preamble inside a CSV is not merely untidy: above the writer's own headers, a
`present_mode=` in the prose **overrides the measured one** and the report then
names a mode on the strength of a sentence; at the very top, the file's own
reader refuses it outright.

Hence provenance is machine-written into the header, prose lives in this file,
and each committed CSV was round-tripped back through `cargo xtask pacing
--analyse` to confirm it reads clean and names the correct granted mode.

The one exception is the host verdict, which the client cannot know: it is
appended by the tool as a final `#` line, after the data. Every key it adds is
`host_`-prefixed, and first-match-wins means a line appended last cannot
override anything the writer said about itself.

## Reproducing this

From the repository root — this matters, because `assets/maps/coil.map` resolves
relative to the working directory, and from anywhere else the client silently
loads an empty plane and measures a scene with no geometry in it:

```sh
cargo build --release --target x86_64-pc-windows-gnu -p straf3-game --bin straf3
./probes/pacing/take-measurements.sh
```

To re-derive the published table from the committed files, with no GPU and no
Windows:

```sh
cargo xtask pacing --analyse probes/pacing/results/static/straf3-fifo-1.csv --table
```

# WHAT THIS IS EVIDENCE FOR
# -------------------------
# r27: the course goals come from the compiled map's own trigger volumes. Nothing
# below was typed into the agent. `probes/coil-course` reached the same finish
# line by having `(0, 3456, 112)` and `y > 3040` written into its source; this
# crate reaches it from `CompiledMap::triggers` and a downward trace, and the
# same program produces the neighbouring file for a map it has never seen.
#
# CROSS-CHECK AGAINST THE KNOWN-GOOD
# ----------------------------------
# The probe published its own trigger table for this map in
# probes/coil-course/results/coil.txt. The two agree exactly:
#
#   volume    probe (coil.txt, H6 and the header table)   this file
#   t_start   START     (-224,32,-32)..(224,64,768)        identical
#   t_cp1     bit 0x04  (-224,1536,-32)..(224,1568,768)    checkpoint 0, identical
#   t_cp2     bit 0x08  (-224,3104,-96)..(224,3136,768)    checkpoint 1, identical
#   t_finish  FINISH    (-96,3424,64)..(96,3488,768)       identical
#
# and so do the compiler's own numbers: 26 solids, 4 trigger volumes, collision
# digest 0x47263b8845d8bb4b, which is the digest the probe's H6 printed. Same
# geometry, same volumes, same order, reached independently.
#
# WHERE THE DERIVED AIM DIFFERS FROM THE HAND-WRITTEN ONE, AND WHY IT MATTERS
# --------------------------------------------------------------------------
# The probe aimed at the finish volume's `mins.z + 48` = z 112, reasoning that
# aiming at the middle of a 704-unit column would aim 350 units into the air.
# That reasoning is right and the rule it produced is coil's geometry: it assumes
# the volume's floor IS its `mins.z`. Here the floor is found by tracing, and it
# is at z=80 — sixteen units above `mins.z`. The derived aim is z 104.1.
#
# On the same map's second checkpoint the difference is not sixteen units. That
# volume's `mins.z` is -96 and the surface a player crosses it on is z=64, so
# `mins.z + 48` would aim 112 units UNDERGROUND. The probe never noticed because
# it only ever applied that rule to the finish.
#
# A SHIPPED TRAP THE PLAN NOW REPORTS
# -----------------------------------
# coil.map's checkpoints declare `"count" "1"` and `"count" "2"`. Nothing reads
# them. straf3-map takes six keys out of a .map — classname, origin, angle,
# angles, target, targetname — and checkpoint numbering comes from the order the
# entities appear in the file (`Checkpoint(*next_checkpoint)` in entity.rs).
# training-crouch-slide.map declares the same key with the same non-effect.
#
# On both maps the two orders agree, which is exactly why nobody has been bitten:
# the plan compares them and reports no contradiction here. It would report one,
# loudly and by name, on a map where they disagreed — a reversal is the first
# geometry where they can — and it would still follow the compiled order, because
# that is the order the shipped game reads. `a_count_key_that_contradicts_source_
# order_is_reported_and_not_obeyed` is the test.
#
# WHAT THIS FILE DOES NOT SHOW
# ----------------------------
# Anything about running the course. No player moves here, no clock starts, and
# the leg distances are straight lines between aim points, not a route: they say
# how far apart the goals are, not how far a run travels. Search and completion
# are the next unit of work.
#
# Read the `turn` column: every leg of the course proper reads 0.0. coil is a
# corridor, and the 22.2 degrees is the spawn walking sideways onto the start
# line. See results/first-party-geometry.md.

-- notes --

  2 checkpoints declare a `count` key and nothing reads it. straf3-map takes classname, origin, angle, angles, target and targetname out of a .map and nothing else; checkpoint numbering comes from source order.

#
# THE VERDICT ASKED FOR: IS THIS MAP TIMEABLE?
# --------------------------------------------
# Yes, and by the shipped compiler rather than by inspection of the .map text.
#
#   - it compiles clean: 10 solid hulls, 4 trigger volumes, zero warnings
#   - `has_timing()` is true and the collider's coverage is 0x0000000f, which is
#     START | FINISH | the first two checkpoint bits
#   - all four volumes resolve their `target` to a real point entity:
#     t_start -> target_starttimer, t_cp1/t_cp2 -> target_checkpoint,
#     t_finish -> target_stoptimer
#   - the spawn is in open air: start_solid=false, all_solid=false, with a floor
#     0.125 units under the hull, which is exactly `SPAWN_CLEARANCE`
#
# So it is a full course skeleton, not a stub with decorative triggers, and it is
# a usable second map for a completion run. Its own header says it "is NOT a
# course" — that is a statement about its design intent (it isolates one
# mechanic and teaches nothing else), not about its timing entities, and the two
# are not in conflict.
#
# ONE THING THE PLAN DOES NOT SHOW, AND A RUNNER MUST KNOW
# --------------------------------------------------------
# The plan is a course of aim points; it says nothing about which INPUTS reach
# them. This map needs one coil never does. Its lintel is a soffit descending to
# z=48 and a standing hull is refused under it, so a run must crouch —
# `crouch_pressed = cmd.up_move < 0 || buttons.contains(CROUCH)` in
# crates/straf3-sim/src/step.rs, and `check_duck` sets `crouched` with no
# headroom test, so crouching down always succeeds and only standing up is
# guarded. Both read directly in the source, not taken on report.
#
# `probes/coil-course`'s bot cannot emit that input at all: its control is
# { yaw_rate, right, forward, jump } and it hardcodes up_move: 0. An agent that
# inherited that alphabet completes coil and is then wedged here permanently.
# That makes this map the cheapest available test of the agent's INPUT alphabet.
#
# WHAT IT DOES NOT DO
# -------------------
# It does not defeat the prior art's shape, and that has to be said plainly. Read
# the `turn` column: 0.0 on every leg. The whole course runs in +y on a floor at
# z=0, from y=16 to y=3280. A bot that maximises `y` and knows nothing else
# reaches every one of these goals in order, exactly as it does on coil.
#
# So this map tests INPUT generality, not ROUTE generality, and only the second
# bears on whether a search reasons about where to go. r11 as amended says it
# outright: completing a monotone corridor such as coil or training-crouch-slide
# does not discharge it, because the sort-triggers-by-axis heuristic completes
# those too. A completion here is worth having — it is a genuine untuned map for
# the checksum contract and by its own header has never been run by a bot — and
# it is not generality evidence. Both of those are true at once.
#
# WHERE THIS AGREES WITH THE MAP SOURCE
# -------------------------------------
# assets/maps/training-crouch-slide.map declares its triggers at lines 364-409
# and their point entities at 422-443. The bounds below are those brushes, as
# compiled: t_start y 0..32, t_cp1 y 2016..2048, t_cp2 y 2496..2528, t_finish
# y 3264..3296. Read against the file, they match. The checkpoint NUMBERING is
# not in the file at all — `count` `1` and `2` are Defrag keys this compiler does
# not read — so cp0 and cp1 below come from source order and nothing else, which
# is the assumption the notes section names.

-- notes --
  ASSUMPTION: the 2 checkpoints are visited in source order. Defrag gives them no explicit index and straf3-map numbers them as it meets them, so a map that declares them out of order gets a plan in that same wrong order. Nothing here can check it
  2 checkpoints declare a `count` key and nothing reads it. straf3-map takes classname, origin, angle, angles, target and targetname out of a .map and nothing else; checkpoint numbering comes from source order. Both first-party maps declare `count`, and on both it happens to agree — reported so the next author does not find out otherwise
  the 2 checkpoints are route guidance, not gates: RunState::finish reads TriggerSet::FINISH alone, so a run that skips them all still produces a time

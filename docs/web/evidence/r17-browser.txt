=== r17 — straf3 running in a browser, on a real GPU ===

The first time in this project's history that a browser number means anything.
Every prior wave ran under WSL2, where Chrome had no hardware WebGPU adapter and
`drive.mjs` reached for `--use-angle=swiftshader` to get a software one. This
host is native Windows with a discrete GPU, so the adapter, the frame pacing and
the present mode below are measurements rather than placeholders.

  host      DESKTOP-G99TTEO — Windows 10 19045, 12 logical cores,
            NVIDIA GeForce RTX 3060 Ti, 1920x1080 @ 165 Hz
  captured  2026-08-28 (UTC), git HEAD f8d8b2e
  URL       http://127.0.0.1:8790/play/coil?p=cpm

------------------------------------------------------------------------------
1. THE URL, AND HOW IT IS SERVED

  crates/straf3-game/web/build.sh          # builds the bundle into web/pkg
  node crates/straf3-game/web/serve.mjs    # serves it on 127.0.0.1:8790

`serve.mjs` mounts `/client/` and `/assets/maps/` and routes `/play/*` to the
shell, so the URL above is opened by hand in any browser on this machine. It is
not a fixture: the same path shape is what `web/dev/serve.mjs` serves on 8787.

Bundle actually downloaded by a visitor (build.sh's own measurement, with
wasm-opt -Oz present — binaryen 132, installed on this host for the purpose):

    straf3_game_bg.wasm      512413 B      213656 B gzipped
    straf3_game.js            99200 B       16405 B gzipped
    TOTAL                                   230724 B gzipped

The `egui`/`epaint`/`ecolor` byte-scan gate in build.sh passed: none present.

------------------------------------------------------------------------------
2. THE BROWSER AND THE ADAPTER

    Chrome/151.0.0.0  (Mozilla/5.0 (Windows NT 10.0; Win64; x64)
                       AppleWebKit/537.36 (KHTML, like Gecko) Safari/537.36)
    navigator.hardwareConcurrency = 12, devicePixelRatio = 1
    screen 1920x1080, canvas 1264x625 CSS px

`navigator.gpu.requestAdapter({powerPreference:'high-performance'})` then
`adapter.info`:

    vendor        "nvidia"
    architecture  "ampere"
    device        ""            <- masked by Chrome (see note)
    description   ""            <- masked by Chrome
    subgroupMinSize 32, subgroupMaxSize 32
    featureCount 19, maxTextureDimension2D 16384

The 3060 Ti is GA104, which is Ampere, so `nvidia`/`ampere` identifies it as far
as the browser will say. `device` and `description` are empty by Chrome's
default privacy policy, not because the adapter is anonymous — revealing them
needs `--enable-webgpu-developer-features`, which was deliberately NOT set so
that this transcript reflects a stock browser.

WHAT `straf3-render` LOGS, and why it cannot be the adapter evidence here:

    straf3-render: backend=BrowserWebGpu adapter="" type=Other
    straf3-render: present_mode=fifo (requested adapter's first)
                   frame_latency=2 available=[fifo]
    straf3-render: map is 312 triangles

`gfx.rs` prints wgpu's `AdapterInfo`, and on the WebGPU backend wgpu can only
report what the WebGPU spec exposes — which does not include an adapter name or
a device type. So `adapter=""` and `type=Other` are structural, not a failure,
and on this backend that line CANNOT name the GPU. The `adapter.info` block
above is the admissible evidence, together with the flag comparison in §5.

    available=[fifo] is a finding in its own right: the browser offers no
    present mode but vsync. There is no mailbox and no immediate, so a browser
    player cannot trade latency for tearing the way the native build can.

`coil.map` is fetched over HTTP and compiled by the wasm build at runtime; the
collision digest above is the browser's own answer. Physics is `cpm`
(4350ccc31bec5d4c) at the canonical 125 Hz, taken from an unqualified
`?p=cpm` link — no `?backend=` was passed, so `pickBackend()` really did call
`requestAdapter()` rather than being told the answer.

Interaction, all confirmed under CDP against the running client:
  - pointer lock taken (`document.pointerLockElement === "straf3-canvas"`)
  - mouse-look turns the view (`look_to` closes the loop on the client's own
    reported yaw, reaching 128.04 deg against a 128 deg request)
  - WASD moves, Space jumps, and strafejumping accelerates past ground speed:
    320 ups walking, 452.9 ups peak in this transcript and 470 ups in a
    sibling run, sustained down the full 1536-unit strafe corridor
  - the run clock started at the start trigger (`run 0:00.776` in telemetry)

The pair is more informative than either alone. A 165 Hz display has a 6.06 ms
budget; the median frame hits it in both windows, and full CPU saturation moves
the median by 0.05 ms. What saturation costs is the TAIL: p99.9 goes 7.3 -> 24.3
ms and the missed-frame rate goes 0.05 % -> 0.36 %, roughly a dropped frame
every 1.5 seconds. That is the honest shape of the risk in a browser.

Both numbers are from a HEADFUL Chrome window on the real display. A headless
number would be a different claim and is not made here.

------------------------------------------------------------------------------
5. THE DEFAULT DRIVER FLAGS DO NOT SILENTLY GIVE SOFTWARE HERE

`drive.mjs` defaults CHROME_FLAGS to `--enable-unsafe-webgpu
--use-angle=swiftshader`, written for a GPU-less WSL2 box. Whether that forces a
software WebGPU adapter on native Windows was an open question, so it was
measured rather than reasoned about. Same URL, same build, flags the only
difference:

  with `--enable-unsafe-webgpu --use-angle=swiftshader`
      navigator.gpu present, requestAdapter() returned NULL
      the client refused, showing its own message:
        "straf3 needs WebGPU, and this browser did not offer an adapter."

  with those flags omitted (what every run above used)
      adapter.info -> vendor "nvidia", architecture "ampere"

So on this host the bad flags produce NO adapter rather than a software one:
the failure is loud and the client stops, rather than quietly recording a run on
a software rasteriser. That is the safe direction, and it is now measured.
All runs above were taken with:

  CHROME="C:/Program Files/Google/Chrome/Application/chrome.exe" \
  CHROME_FLAGS="--no-first-run --no-default-browser-check" \
  node crates/straf3-game/web/drive.mjs \
       crates/straf3-game/web/steps/r17-evidence.json --headful

------------------------------------------------------------------------------
6. THE VERDICT r17 ASKS FOR: PLAYABLE, OR MERELY RUNNING?

Merely running is comfortably beaten. It loads, takes the pointer, turns with
the mouse, and strafejumps to 450+ ups down a real course at a locked 165 Hz
with a 6.1 ms median. On the evidence here the rendering and input path are not
what would stop someone competing in a browser.

What this transcript does NOT establish, and neither should anything citing it:

  - NOBODY HAS PLAYED IT. Every input above was dispatched by `drive.mjs` over
    CDP. Input latency as felt by a hand is not measured, and `frame_latency=2`
    with fifo as the only present mode is exactly where a browser would be
    expected to lose to the native build. A scripted driver cannot notice that.
  - NO RUN WAS FINISHED, so this is not r18 or r19 evidence. `RunSink` fires
    only on crossing the finish trigger. The scripted driver reaches the ramp
    wave at ~450 ups and is stopped by the optimisation coil's own header
    documents ("575 ups lands you flat on the pad ... below it you land on
    ramp_c's 45-degree face and the clip into that plane takes most of your
    speed away"). The bot is defeated by the course's difficulty, which is a
    statement about the bot, not about the browser.
  - The 120 Hz browser class in VISION section 9 is not settled by one machine
    with a discrete GPU on localhost. This is an existence proof on good
    hardware, not a claim about the median visitor.
